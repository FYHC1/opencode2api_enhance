# 阶段化计划驱动交付（Phased Plan-Driven Delivery）

**项目**: opencode2api  
**用途**: 人 + 多 AI 协作时的**元规范**——如何切阶段、写计划、交接执行、独立验收。  
**计划实例目录**: `docs/ai-framework/plans/`（若已有 `docs/superpowers/plans/` 可继续用，二者择一为主并在计划里写清）。  
**OpenCode 入口**: `/plan-phase`、`/accept-phase`、`/handoff`（见 `.opencode/commands/`）。

本文件**不是**某一功能的实施计划；实施计划按阶段另存。

---

## 1. 一句话

**先对齐边界 → 写可执行阶段计划（含验收与交接提示词）→ 执行方按 Task 落地并交证据 → 独立验收 → 缺陷写入下一阶段。**

规划/验收与执行宜分离；验收只认证据，不认「应该能过」。

---

## 2. 八步循环

| 步 | 名称 | 做什么 | 产出 |
|----|------|--------|------|
| 0 | 定边界 | 一句话目标；做/不做；红线（密钥、合规、YAGNI） | 口头约定或 STATUS 数段 |
| 1 | 摸现状 | 分支、与 main 差、已有能力、单测/产物 | 基线快照 |
| 2 | 写阶段计划 | Task 可 commit；每 Task 有测法 | `docs/…/plans/YYYY-MM-DD-phase-….md` |
| 3 | 写交接提示词 | 贴计划文末，可整段复制 | 「给接手 AI 的完整提示词」 |
| 4 | 执行 | 严格 Task 1→N；小步可审查的 commit | 功能分支 + 提交链 |
| 5 | 执行方自证 | 跑测试/构建，自评验收表 | 命令输出、产物路径 |
| 6 | 独立验收 | 另一会话/角色：对照表 + 复跑 + 红线 | 通过 / 有条件通过 / 不通过 |
| 7 | 下一阶段 | 通过或有条件通过 → 新计划 + 新提示词；缺陷进下阶段 Task 1 | 阶段 N+1 计划 |

---

## 3. 角色

| 角色 | 职责 | OpenCode |
|------|------|----------|
| 规划 | 定阶段、写计划与提示词、合并策略 | `@phase-planner` / `/plan-phase` |
| 执行 | 只按计划 Task 实现、自测、交证据 | 外部 AI 或本会话（用计划文末提示词） |
| 验收 | 对照验收表、复跑命令、给结论与下阶段 | `@phase-acceptor` / `/accept-phase` |
| 人类 | 定范围、手工点验、是否 push、是否放宽 | — |

**原则**: 规划方写提示词 → 执行方落地 → 验收方独立判。同一对话既写又做又自判「全绿」风险更高。

与**单次提交审查**（`/review`、`CODE_REVIEW.md`）的区别：审查偏一次 diff；本方法论偏**整阶段**对照验收表。

---

## 4. 阶段计划必须包含的类别

| # | 类别 | 说明 |
|---|------|------|
| 1 | 元信息 | Goal / Architecture / Tech / 状态 / 分支名 |
| 2 | 全局约束 / 红线 | 冲突时以本节为准；密钥不进 git 等 |
| 3 | 阶段地图 | 前后阶段；本阶段边界 |
| 4 | 文件与契约 | 改哪些文件；配置/API 契约 |
| 5 | **功能 Task** | 有序、可测、可 commit |
| 6 | **测试** | 单测/集成/构建命令与期望 |
| 7 | **验收标准总表** | 编号 + 通过条件 |
| 8 | 风险与降级 | 做不完怎么砍 |
| 9 | **交接提示词** | 零上下文可执行 |
| 10 | 残留 / 已知缺陷 | 不阻塞则带入下阶段 Task 1 |

主干：**边界 + 功能 Task + 测试 + 验收表 + 交接提示词**。

### 单个 Task 最小结构

```text
Task N：一句话目标
  Files：创建/修改/测试路径
  行为或契约：做成什么样
  Steps：实现 → 跑哪条命令 → 期望输出
  Commit：一条约定格式的说明（见 AGENTS.md / 项目 Git 规范）
```

### 文件名与位置

```text
docs/ai-framework/plans/YYYY-MM-DD-phase-<slug>.md
# 或
docs/superpowers/plans/YYYY-MM-DD-phase-<slug>.md
```

空白骨架也可从 `docs/ai-framework/phase-plan.template.md` 复制。

---

## 5. 交接提示词五段结构

文末「给接手 AI」整段必须含：

1. **基线** — 目录、从哪分支拉、已完成阶段、必读计划路径  
2. **做** — 本阶段目标列表（对应 Task）  
3. **不做** — 红线与范围外（抄 Global Constraints）  
4. **工作方式** — 先测基线、按 Task 顺序、证据优先、提交规范、回复语言  
5. **交卷** — 分支名、commit 列表、验收表自评、测试/构建结果、残留风险  

开头建议明确：**完整执行本阶段，不要只写方案。**  
**默认不 `git push`**，除非人类写进计划并授权。

---

## 6. 验收输出四段（强制）

1. **基线** — 当前分支、tip、main 是否已含本阶段  
2. **对照表** — 计划验收表逐项 ✅ / ⚠️ / ❌ + 证据  
3. **结论** — 通过 / 有条件通过（列缺陷）/ 不通过（列阻塞）  
4. **下一步** — 下阶段要点；缺陷必须进下阶段 Task  

**有条件通过合法**：主路径齐备 + 已知缺陷显式写入下一阶段，不假装全绿。

---

## 7. 阶段切分规则

1. 一阶段一个可演示增量。  
2. 计划内写死「明确不做」。  
3. main 合并、是否 push 写进计划；默认不 push。  
4. 密钥与破坏性操作永远在红线里（按各项目补充，如不提交 `.env`、凭证、私钥）。

## 9. OpenCode 命令对照

| 命令 | 代理 | 何时用 |
|------|------|--------|
| `/plan-phase` | `@phase-planner` | 讨论结束，要出阶段计划 + 提示词 |
| `/accept-phase` | `@phase-acceptor` | 执行方声称完成，要独立验收 |
| `/handoff` | 命令内嵌 | 只要可粘贴执行提示词 |
| `/review` | 风格/测试/依赖 | **单次提交前**审查（与阶段验收互补） |

不用 OpenCode 时：把计划文末提示词贴给任意执行 AI；验收时把本节 §6 发给验收 AI。

---

## 10. 原则四条

1. **边界先于功能**  
2. **计划必须可交接**（零上下文提示词）  
3. **任务必须可验证**（命令 + 期望）  
4. **验收独立且认证据**（缺陷显式带入下阶段）
