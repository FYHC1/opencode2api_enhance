## 二、⚠️ N2 实质缺陷：`stop_scan_concurrency` 是死配置

**现象**：前端有配置面板（默认 4）、后端有配置项+校验（1~8 回退 4）、按钮 title 显示"停止扫描（4 并发）"——**但没有任何代码使用这个值**。

**证据**（代码级）：
- 后端停止逻辑 `core/manager/probe.go:120 RequestStop()`：仅把状态 `Running → Stopping`；
   worker 退出靠 `isStopping()` 检查，**停止速度取决于 worker 数（= scan_concurrency），与 stop_scan_concurrency 无关**。
- 全仓 grep：`StopScanConcurrency` 只在 `config.go`（定义/校验/读写）和 `config_test.go` 出现，
  **probe 扫描逻辑零引用**。
- 前端 `api.scanStop()` 不传参，停止请求无并发参数。

**结论**：用户配置"停止扫描并发 4"后——**停止行为完全不变**，只是 title 上显示了个数字。属"看起来做了、实际没做"的半成品。

**修复建议**（需明确停止并发的语义）：
- `RequestStop()` 改为可传 `concurrency`：把 worker 收尾限制为最多 N 个并发继续处理
  （其余立即返回），或按用户原意"停止时只保留 N 个 worker 清理"；
- 或明确语义为"停止确认后最多等 N 并发收尾"，配置透传到 `ScanStatus`/停止流程；
- 若产品上停止就是"全部立刻退出"，则该配置项本不存在——**需用户拍板停止并发的真实含义**，
  再决定接逻辑还是砍配置。
