# 性能模式说明

> 写在这份文档最前面的话：**我希望你永远也用不上它。**

---

## 一、为什么会有性能模式

在某一段时间里，opencode的deep-v4-flash 发布之后，对话出现了非常严重的卡顿。

我排查了很多。除了 opencode 自身的原因外，我能做的，就是尽可能弥补其他方面带来的延迟问题：

- 节点质量参差不齐，每个节点对应一个实例，但是有时候一个节点"10 秒没响应，过 10 秒又恢复"，说不能用吧还能用，说能用吧又时常不能用。且**用户不可能时刻手动持续检查每一个节点**；
- 节点冷却机制是被动的——只有请求失败了才记一笔，坏节点不在冷却期里照样会被选中。

于是我做了**性能模式**：让应用自己去发现问题、自己绕开坏节点、自己恢复，全程不需要你手动检查。请注意，这会加快检查的频率，对**你电脑的资源占用**而言多了一些后台开销——尽管这有违我的初心。不过您也可以放心，实际占用非常小。

---

## 二、我做了什么

一句话：**应用替你盯住每一条链路，自动剔除坏节点，恢复后自动回归，全程无感。**

### 1. 链路级主动探活

每隔一段时间（默认 45 秒，这里用户可自己配置），应用会经每个实例的真实出口发送一次轻量探测请求，测量整条链路——从本地出口到远端服务——的**延迟与成败**，而不是只看端口通不通。

- 能发现"端口通、链路抖"的断断续续场景；
- 每次探测超时很短（默认 3 秒），不会影响正常使用；
- 并发探测有上限，不会造成"探测风暴"。

### 2. 滑动窗口质量评分

最近一段时间（默认 10 分钟窗口，这里用户可自己配置）内，综合三件事给每个实例打分（0~100）：

- **成功率**：探测成功了多少次；
- **平均延迟**：快还是慢；
- **连续失败**：最近是不是一直在失败。

分数对应四个等级，在实例池页直接可见：

| 等级 | 颜色 | 含义 |
|---|---|---|
| healthy | 🟢 绿 | 链路健康 |
| degraded | 🟡 黄 | 变慢，降权 |
| flaky | 🟠 橙 | 抖动，跳过 |
| down | 🔴 红 | 不可用，剔除 |

新实例没有历史数据时按健康处理，不会被误伤。

### 3. 质量加权路由

路由选择节点时，质量分说了算：

- 分数高的优先；
- degraded 降权、flaky 跳过、down 直接剔除；
- 同时，真实请求的成败与延迟也会实时回填——**探活 + 实测量双通道**，请求一旦失败，很快就能反映到分数上。

### 4. 熔断 + 半开自动恢复

这是最"省心"的部分：

- 某个节点连续失败达到阈值（默认 3 次，可配置），自动进入**熔断**，路由不再选中它；
- 熔断一段时间（默认 60 秒，可配置）后，自动放行 **1 个探测请求**：
  - 成功 → 自动回归池子（半开恢复）；
  - 失败 → 继续熔断，直到它真正恢复。

**坏节点自动剔除、恢复自动回归，你什么都不用做。**

### 5. 可视化与参数

- 实例池页：每个成员显示**质量分徽标** + 平均延迟，悬停可见成功率与连续失败次数；随时可点「立即探活」手动触发一轮；
- 实例池页/设置页：**性能模式开关**——关闭后路由行为与旧版完全一致；
- 设置页：探活间隔、质量窗口、熔断阈值、半开间隔全部可调，**保存即热生效**，无需重启。

> 这些参数都有默认值，**日常不需要动**。只有当你的网络环境特殊时，才值得按实际情况微调。

## 三、一些小的优化

除了性能模式，还顺手做了几件让日常使用更顺手的事：

1. **探针进程泄漏修复**
   修复了节点扫描时探针进程残留的问题——之前每扫描一轮就可能留下数十个进程（最多见过 90+ 个），现在无论成功失败都会清理干净。

2. **残留进程一键清理**
   万一历史版本已经留下了"占着进程但没在使用"的孤儿节点/探针进程——设置页新增「残留进程清理」：点一下探测，勾选，一键清除。**运行中的实例和网关会自动跳过，不会被误伤。**

3. **实例池释放进度全局可见**
   一键释放全部池成员时，右下角会有全局进度面板，实时显示释放进度，不再"点了没反应"。

4. **节点池交互优化**
   扫描按钮移到更顺手的入口；组头/行内复选框的误触问题修复。

5. **移除冗余导出功能**
   去掉几乎无人使用的 CSV/JSON 导出入口，界面更干净。

6. **修复窗口图标不显示**
   左上角图标在特定环境不显示的问题已修复。
