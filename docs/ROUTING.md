# 路由机制说明（Route Modes）

> 本文档说明 opencode2api 统一网关的路由模式：**负载均衡（round_robin）**、**故障转移（failover）** 和 **默认模式（failover + 健康计数，推荐）**。
> 面向使用者与开发者，涵盖各模式的行为、参数与配置方式。

---

## 一、三种模式总览

| 模式 | 别名 | 核心思想 | 适用场景 |
|------|------|---------|---------|
| **负载均衡** | round_robin | 每次请求轮询分发到不同实例 | 节点都健康、希望均摊流量 |
| **故障转移** | failover | 锁一个实例用，失败才换下一个 | 默认的历史模式，简单直接 |
| **默认模式（推荐）** | failover + 健康计数 | 故障转移 + 超时检测 + 计数淘汰 | **生产推荐**，兼顾稳定与容错 |

---

## 二、负载均衡（round_robin）

### 行为
- 维护一个游标，**每次请求游标 +1**，请求分发到对应实例
- 跳过"临时不可用"的实例（见下）

### 优点
- 流量均匀分散到所有实例
- 没有"单点压力"

### 缺点
- 可能命中异常实例（健康度低/冷却中的节点轮到时仍会被尝试）
- 对"免费额度"型节点不友好（均匀轮询会让每个节点都快速消耗额度）

### 配置
```json
{ "route_mode": "round_robin" }
```

---

## 三、故障转移（failover）

### 行为
- 维护一个游标，**成功不动游标**，**失败才切换到下一个健康实例**
- 锁定一个实例持续使用，直到它出错

### 流程
```
实例1 可用 → 一直用
   ├─ 故障(429/401/5xx/连接失败) → 切换实例2
实例2 可用 → 一直用
   ... 直到最后一个 = 1 轮
```

### 优点
- 稳定：锁一个健康实例，减少无谓切换
- 简单：逻辑直白

### 缺点
- **没有超时检测**：如果实例"挂起"（连接建立了但迟迟不吐数据），会一直干等
- **没有健康记忆**：反复失败的实例会被反复尝试，浪费请求

### 配置
```json
{ "route_mode": "failover" }
```

---

## 四、默认模式（推荐）：failover + 健康计数

### 行为
在**故障转移**基础上，增加：
1. **超时检测**（首字 / 静默）
2. **故障计数**（跨轮累计，3 次淘汰）
3. **成功清零**（恢复健康）

### 完整流程
```
实例1 可用 → 一直用
   ├─ 故障(429/401/5xx/连接失败) → 计数+1 → 切换实例2
   ├─ 超过 X 秒无响应（一个字都没收到）→ 计数+1，错误"延迟>X s" → 切换实例2
   └─ 回复到一半，卡住超过 Y 秒 → 计数+1 → 切换实例2
实例2 可用 → 一直用 ... 直到最后一个 = 1 轮
```

### 健康计数规则
- **计数 +1**：每次故障/超时
- **满 3 次** → **停止该实例**（不从池中移除），把错误信息展示给用户
- **用户手动重启实例** → 计数清零（重新开始）
- **某轮正常** → 计数清零（后续异常从 1 重新计数）
- 计数**跨轮累计**（一轮 = 从实例1 依次用到最后一个实例）

### 时间参数（可配置）
| 参数 | 默认值 | 白话含义 |
|------|--------|---------|
| **首字超时（TTFT）** | 10s | 发请求后干等 X 秒一个字没收到 → 换实例 |
| **静默超时** | 5s | 回复到一半，卡住 Y 秒没新内容 → 换实例 |
| **总超时** | 不设 | 长任务不限制（避免掐断正常长回复） |

### 为什么推荐
- **稳定**（继承故障转移的"锁节点"）
- **不干等**（超时检测兜底）
- **自我修复**（计数淘汰坏实例 + 重启恢复）

### 配置
```json
{ "route_mode": "failover" }
```

> 注：默认模式当前仍使用 `failover` 作为 route_mode 值，健康计数逻辑作为附加层启用。

## 五、参数速查表

| 参数 | 默认值 | 说明 |
|------|--------|------|
| route_mode | `failover` | `failover` / `round_robin` |
| 首字超时 | 10s | 干等多久无响应就切换 |
| 静默超时 | 5s | 中间卡住多久就切换 |
| 坏池阈值 | 3 次 | 故障计数满几次停止实例 |
| 总超时 | 不设 | 长任务不限制 |
| 并行预热数量 | 待定 | 对话时并行预热的后续实例数 |
| 预热缓存时长 | 15s | 预热结果缓存多久可复用 |

## 六、并行预热（快速故障跳转）【优化方向】

### 需求
用户发起一次对话请求时，**并行探测后续实例**（预热），当前实例超时不回复时，**快速转移到已探测通过的实例**，避免现场串行探测的延迟。

### 机制
```
用户发起对话请求
  ├─ 实例1 开始正常请求
  └─ 【并行】预热游标之后的 X 个实例（用真实最小对话请求探测）
如果实例1 超时不回复 → 查预热缓存：
  ├─ 缓存里有健康实例 → 立即切换到该实例（快）
  └─ 缓存里没有健康实例（这一批都不行）→ 跳过这一批，请求下一批的第一个
      且这一批全部标记故障 +1（错误标记为"延迟>X s"）
```

### 规则
- **预热范围**：游标之后的 X 个实例（不是全池），X 可配置
- **探测方式**：真实最小对话请求（`max_tokens:1` 级别，真实可靠，会消耗少量额度）
- **缓存**：预热结果保留 N 秒（默认 15s），期间复用，避免每请求都探测
- **切换**：超时 → 用缓存健康实例；缓存空/无健康 → 跳过这批，游标跳到下一批第一个
- **计数**：预热失败的实例标记 +1（"延迟>X s"），满 3 次停止实例（与主规则一致）
- **下一批**：游标直接跳到下一批的第一个实例，继续预热后续

### 配置项（设置页）
| 配置 | 默认 | 文案 |
|------|------|------|
| 并行预热数量 | 待定 | 对话时，并行预热实例的数量【】，为故障做快速跳转 |
| 预热缓存时长 | 15s | 预热结果缓存时长：【】秒 |

## 七、后续优化方向

### 1. auto 模型（智能节点选择）【已确认，优先】
- 提供一个虚拟模型名 `auto`：用户填 `model: "auto"`，网关**自动选择健康 + 速度快的节点**，无需用户理解路由。
- 支持**权重配置**：兼顾速度与质量（如"延迟优先"或"可用率优先"）。
- 本质是"质量分排序路由"的用户友好封装（可用率 × 延迟 × 权重）。

### 2. 质量分排序（参考 model-gateway）
- 为每个实例维护**滑动窗口可用率 + 平均延迟**（窗口 20 条）。
- 路由选择按 `(-可用率, 延迟)` 排序，坏实例自动降权、好了自动回升。
- 注意：可用率由**探测**驱动、失败计数由**请求**驱动，两套信号分离。

### 3. 流预检 Prime（参考 enhance_2）
- HTTP 200 后 12s 内必须见到**真实模型输出**（非空 delta/text/reasoning/tool_calls），否则判死流 → 标记失败 → 换候选重试，**客户端无感知**。
- 与流内超时（TTFT/静默）互补：prime 挡"建流前死"，流内超时挡"建流后挂"。

### 4. 巡检预算（参考 model-gateway）
- 每日巡检次数预算 + 每日强制巡检 + 手动全检重置计时，防止探测打爆免费 API 额度。

### 5. 跨模型回退（需谨慎，评估后做）
- 模型级回退（此模型 429 换下一个免费模型）**仅配合质量分**：只回退到质量分接近的模型。
- ⚠️ 若免费模型质量差异悬殊（只有一个好用），无脑跨模型回退 = 垃圾模型浪费额度，**弊大于利，不单独做**。

### 6. 模型×实例矩阵（不建议单独做）
- ⚠️ 已评估：仅当候选模型质量接近时才有意义；否则是"垃圾模型×好实例"的无效尝试。**不列入主路径**，仅作为质量分排序的兜底。

---

## 八、决策记录（利/弊评估）

> **既定前提**：免费模型质量必然参差不齐（有的好用、有的拉胯）。所有涉及"多模型选择"的优化都必须基于这一现实评估——**不做**任何"假设所有模型质量接近"的设计（如无脑跨模型回退、模型×实例矩阵）。此前提记录于此，非现阶段实施，供未来优化参考。

| 候选方案 | 利 | 弊 | 结论 |
|---------|----|----|------|
| 跨模型回退链 | 多模型可用时提升可用性 | 单好模型时垃圾模型浪费额度 | 配合质量分才做 |
| 模型×实例矩阵 | 全覆盖尝试 | 质量悬殊时纯浪费 | 不做主路径 |
| auto 模型 + 权重 | 用户友好、兼顾速度质量 | 需实现质量分 | ✅ 优先做 |
| 质量分排序 | 自动降权坏节点 | 需探测数据积累 | ✅ 做 |
| 流预检 Prime | 客户端无感挡死流 | 与现有超时重叠需整合 | ✅ 做 |
| 巡检预算 | 防探测打爆额度 | 实现成本 | ✅ 做 |
